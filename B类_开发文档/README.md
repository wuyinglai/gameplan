## 📁 目录结构

```
B类_开发文档\
├─ 🔴 开发规划\
│  ├─ 🔴 开发规划.md       ← 🔴 **唯一执行顺序**（阶段 · 单元 · 指令 三层 · 每条指令的意义）
│  └─ 最小测试单元规划_初版.md  ← 初版规划（背景资料，不据此执行）
├─ 基础文档\      ← 施工图（做什么 · 数据结构 · 模块划分）
└─ 开发用例\      ← 测试用例（怎么验 · 测的时候填结果）
```

**每个单元配两个文件**：

| 放在 | 命名 | 装什么 |
|:--|:--|:--|
| `基础文档\` | 🔴 `第NB类_<单元名>.md` | **施工图** —— 做什么 · 数据结构 · 模块划分 · 实施顺序 |
| `开发用例\` | 🔴 `第NB类_测试用例.md` | **测试用例** —— 怎么验（每个单元 15 条左右） |

> 🔴 **为什么拆成两个地方**：施工图**相对稳定**，测试用例**会被反复修改**（每跑一次填一次实际结果）—— 混在一起会互相拖累。

## 🔴 执行顺序

```
01 旅行基础        ← 多个后续系统的共同地基，先做
      ↓
02 商队生存与地点    ← 建立"路上消耗、抵达恢复"的循环
      ↓
03 事件系统        ← 接入已有的时间 / 旅行 / 资源
      ↓
04 探索与信息发现    ← 验证发现状态与调查流程
      ↓
05 战斗与战斗后果   ← 战斗作为旅行中的一种流程
      ↓
06 跑商闭环        ← 交易与订单接入旅行 / 地点 / 资源
      ↓
  跨系统整合测试    ← 重点查连接处，不从头重测
```

**⚠️ 顺序只是建议** —— 如果某个单元依赖的基础规则还没定，**可以先补规则，不必为守顺序而阻塞**。

## 三条判定原则

| # | 原则 |
| :-: | :-: |
| 1 | 🔴 **一个单元做完就该能独立跑起来** —— 能"走一趟"、能"买一次东西"，而不是只写完代码没得看 |
| 2 | 🔴 **规则能跑 ≠ 已平衡** —— 未定稿的数值一律标「**暂定 / 待验证**」，不许因为"跑起来了"就当成调好了 |
| 3 | 🔴 **本阶段只抓严重问题** —— 会阻断流程、造成规则冲突、破坏核心体验、让玩家无法恢复的；表现细节记录后排期 |

## 每个单元文档的十节结构

| # | 节 | 写什么 |
| :-: | :-: | :-: |
| 0 | **这个单元要证明什么** | 目标 + 🔴 明确**不做什么**（防范围膨胀） |
| 1 | **涉及哪些 A 类的哪几节** | 精确到节号 |
| 2 | **数值表** | 明确哪些是**暂定** |
| 3 | **状态清单** | 这一单元游戏里有哪些状态、各怎么变 |
| 4 | 🔴 **代码从哪开始** | 第一个文件 · 数据结构 · 模块划分 |
| 5 | 🔴 **流程图** | 一次完整流程的调用链 |
| 6 | 🔴 **调试怎么看** | 出错了怎么查 |
| 7 | **测试步骤 + 预期结果** | 测试者照着就能跑 |
| 8 | **边界情况表** | 资源不足 / 时间不足 / 重复触发 / 撤退 |
| 9 | **通过标准 + 已知问题** | 出现什么算过；发现的问题记这儿 |
