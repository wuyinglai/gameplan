## 一、总原则

### 1.1 最终目标

完成一个**可实际操作、可以验证核心玩法**的测试版。

测试版不要求拥有正式版的全部美术、地点和内容，但必须包含足以验证核心体验的一组完整系统。

### 1.2 🔴 本轮调整的七条主要决定

| # | 决定 | 🔴 意味着什么 |
|:-:|:--|:--|
| 1 | 🔴 **旧代码停止作为正式开发基础**，不再在旧实现上持续修补 | 🔴 **新代码从零写** |
| 2 | 🔴 **旧代码保留归档**，仅供必要时参考，不直接作为新代码 | 🔴 **不删除，但不使用、不维护** |
| 3 | 🔴 **设计文件、用户裁定、问题清单、有价值的测试思路继续保留** | 🔴 **不因重写代码而推倒重来** |
| 4 | 🔴 **新代码按统一的阶段规划重新实施** | 🔴 见 §二 |
| 5 | 🔴 **每个中阶段完成后：自动验证 → 进度同步 → 项目主人工验收** | 🔴 见 §四 |
| 6 | 🔴 **项目主不需要读懂源代码才能验收，但应逐步理解基本代码架构** | 🔴 见 P1 / 1.0 |
| 7 | 🔴 **最终通过整合测试，把各系统组合成可操作的完整测试版** | 🔴 见 INT |

### 1.3 🔴 一条底线

> 🔴 **自动测试通过 ≠ 阶段通过。**
> 🔴 **「代码写完」「测试通过」「人工验收通过」是三件不同的事**，🔴 不许混为同一状态。

## 三、🔴 旧代码与新代码的处理原则

### 3.1 旧代码

- 🔴 **停止继续开发**，不再作为新版本的代码基础
- 🔴 **保留完整、可识别的归档或版本快照** —— ✅ `90_历史与废案\16_旧代码_20261020_停止维护\`
- 🔴 **不要求逐行审查全部旧代码**
- 🔴 **不因为旧代码曾经通过测试，就认定其实现必须保留**
- 🔴 **不因为决定重写，就删除已有的设计资料、问题清单和有效测试思路**

### 3.2 新代码

| # | 原则 | 🔴 落地 |
|:-:|:--|:--|
| 1 | 🔴 **确定唯一的新代码工作目录** | 🔴 **`游戏本体\src\pNN\`**（P1 = `p1\`） |
| 2 | 🔴 **明确新旧代码的边界，避免两套实现混用** | 🔴 新代码在 `src\pNN\` · 旧代码在 `90_历史与废案\16_...\` —— 🔴 **两者永不互相 import** |
| 3 | 🔴 原有开发技术与工具可作参考，但**不能未经核实直接复用** | 🔴 TypeScript + vitest **沿用**（🔴 不换栈） |
| 4 | 🔴 **不因为重写代码而随意更换技术栈** | ✅ **TypeScript + vitest 不变** |
| 5 | 🔴 **新代码从最小可运行、可测试的架构开始** | 🔴 见 P1 / 1.0 |
| 6 | 🔴 **每次实现都必须有对应的自动验证和可追踪记录** | 🔴 见 §四 第三、四步 |

### 3.3 设计文件与历史资料

- ✅ **继续使用现有权威规则作为设计依据**（`0A_权威系统文档\`）
- 🔴 **已明确的规则直接按规则实现**
- 🔴 **存在冲突、缺失或尚未裁定的规则 → 先登记并处理，不允许 AI 自行猜测**
- 🔴 **历史测试和开发回执仅作参考** —— 🔴 **不能把旧版本的测试通过记录直接当作新代码的通过证据**

## 四、🔴 统一编号方式

### 4.1 三级编号

| 级 | 格式 | 例 |
|:--|:--|:--|
| **大阶段** | `PN` | `P1` |
| **中阶段** | `N.M` | `1.0` `1.1` `1.2` |
| **小阶段** | `N.M.K` | `1.0.0` `1.0.1` `1.1.0` |

### 4.1之二 🔴 🔴「施工步」不是「小阶段」（2026-10-21 项目主定）

🔴 **我把一层文件切成了「施工步」，🔴 那是切分方式，不是规划里的编号。**

| 叫法 | 是什么 | 🔴 验收粒度 |
|:--|:--|:--|
| 🔴 **大阶段 P** | 规划里的正式编号 | —— |
| 🔴 **中阶段 N.M** | 🔴 **🔴 验收单位** —— 🔴 **做完一个才让项目主测一次** | 🔴 **提验收** |
| 🔴 **小阶段 N.M.K** | 规划里的正式编号 | 🔴 **不单独提** |
| 🔴 **施工步**（🔴 我切的） | 🔴 **施工序列文件里的「第 N 步」** —— 🔴 **对齐中阶段，不是再往下切** | 🔴 **不单独提** |

🔴 **对照表（🔴 一眼看懂）**：

| 阶段 | 中阶段 | 施工步 |
|:--|:--|:--|
| **P1** | 1.0 · 1.1 · 1.2 · 1.3 · 1.4 | 第 1~5 步 · 🔴 **一一对应** |
| **P2** | 🔴 **还没划中阶段** | 第 1~5 步 · 🔴 切分方式 |

🔴 **结论**：🔴 **一个 P 阶段 = 一次验收**，🔴 不管内部切成几步。

## 五、🔴 所有中阶段统一的工作流程

> 🔴 **不能因为代码可以运行就直接宣布通过。**

### 第一步 · 明确工作范围

确认本中阶段的：**目标 · 输入依据 · 需要实现的功能 · 明确不做的内容 · 验收条件**。
🔴 发现依赖的规则存在冲突 → **先登记问题并明确由谁处理**。

### 第二步 · 执行开发任务

Hermes 按已确定的范围逐项实施。
🔴 **一次只处理一个明确的小阶段**，避免顺手改动大量无关代码、其他系统规则或未授权的设计内容。

### 第三步 · 自动验证

执行当前小阶段和中阶段要求的测试、类型检查或其他项目检查。

🔴 **必须报告实际执行结果**：通过数量 · 失败数量 · 跳过数量 · 类型检查或其他检查结果 · 尚未解决的问题

> 🔴 **不能把未执行的测试算作通过，也不能只报告"测试成功"而不保留证据。**

### 第四步 · 同步开发进度

由 🔴 **WorkBuddy** 更新唯一项目总控台（§六）。

**必须记录**：本中阶段实际完成了什么 · 当前代码版本或对应提交 · 自动测试与检查结果 · 当前状态 · 仍存在的问题 · 是否需要项目主裁定 · 人工验收需要做什么 · 下一步由谁负责。

> 🔴 **在进度同步完成之前，不得要求项目主自己阅读多个文件来判断目前做到哪里。**

### 第五步 · 项目主人工验收

WorkBuddy 提供**简明、可执行**的人工验收说明（格式见 §七）。

**说明至少包括**：从哪里启动或进入测试 · 需要做什么操作 · 预期看到什么结果 · 实际结果应该记录在哪里 · 遇到什么情况需要判定失败

> 🔴 **项目主不需要阅读源代码，也不需要自行设计测试步骤。**

🔴 **人工验收有三种结果**：
| # | 结果 | 后续 |
|:-:|:--|:--|
| 1 | 🔴 **通过** | 同步状态 → 允许进入下一中阶段 |
| 2 | 🔴 **不通过，需要修改** | 负责人处理 → 提供验证结果 → 重新同步 |
| 3 | 🔴 **发现规则或设计问题，需要先裁定** | 🔴 **先裁定规则**，🔴 再改代码 |

### 第六步 · 处理验收结果并再次同步

🔴 相关负责人必须处理问题并提供验证结果。
🔴 **WorkBuddy 更新对应记录，保留最新状态与历史结果，避免旧回执覆盖新结果。**

### 第七步 · 允许进入下一中阶段

🔴 **只有**以下全部成立才能进入下一中阶段：
- ✅ 自动验证符合要求
- ✅ 必要的人工验收通过
- ✅ 进度已经同步
- ✅ 不存在未处理的重大阻断问题

## 五之三、🔴🔴 验收粒度 = 中阶段，🔴 不是小阶段（2026-10-21 项目主定）

> 🔴 **项目主原话**：「完成一个中阶段我才验收，因为你每完成一个小阶段都要让我来测一遍，
> 那我就得不停地测。🔴 **完成一个中阶段，有明确的需要我测的东西的时候，我再来测**，
> 🔴 不是说做完一个功能我测一遍。」

### 🔴 为什么要定这条

🔴 **P1 被切成 5 个小步**（1.0 骨架 · 1.1 时间体力 · 1.2 天气路况 · 1.3 地图移动 · 1.4 验收）。
🔴 **如果每做完一个小步就催项目主验收** —— 🔴 **一个 P1 要测 5 次**，🔴 后面 7 个阶段就是 30+ 次。

🔴 **项目主每天要管三个 AI**，🔴 **测一次的开销是真金白银** —— 🔴 **不值得为一个小功能花一次。**

### 🔴 两条规矩

| # | 规矩 | 🔴 后果 |
|:-:|:--|:--|
| 1 | 🔴 **WorkBuddy 不在小步完成后催验收** | 🔴 项目主被无意义地打断 |
| 2 | 🔴 **只有「中阶段完成」才提验收**，🔴 而且要满足下面的条件 | —— |

### 🔴 什么时候才可以提验收（三个条件全满足）

| # | 条件 | 🔴 怎么判断 |
|:-:|:--|:--|
| 1 | 🔴 **中阶段的中阶段全部做完** | 🔴 例：P1 = 1.0~1.4 全部 |
| 2 | 🔴 **自动验证已过**（测试 + 类型检查） | 🔴 🔴 **我自己跑过了才算**，🔴 不是 AI 说「做完了」 |
| 3 | 🔴 **有「项目主能亲手看到的东西」** | 🔴 一条命令能跑出结果 · 🔴 或者有一张能读的表 |

### 🔴 🔴 不满足条件 3 时不许提

| 情况 | 怎么办 |
|:--|:--|
| 🔴 只做了「加几个字段」这类事 | 🔴 **不提**，🔴 等整个中阶段做完 |
| 🔴 测试跑不了 · 也没法演示 | 🔴 **不提**，🔴 🔴 **先做出能跑的东西** |
| 🔴 有重大问题正在修 | 🔴 **不提**，🔴 修完再提 |

### 🔴 提验收时给什么（🔴 项目主只看这些）

| # | 给什么 |
|:-:|:--|
| 1 | 🔴 **一条命令**（🔴 复制粘贴就能跑） |
| 2 | 🔴 **10 行摘要**（按 §七 格式） |
| 3 | 🔴 **一张中文表**（项目 · 预期 · 实际 · 对不对） |
| 4 | 🔴 **要他回答的问题**，🔴 🔴 **不超过 3 条** |

### 🔴🔴 一条指令 = 一个中阶段（🔴 2026-10-23 项目主改口径）

> 🔴 **项目主原话**：「这次我们做完，好像问题并不是很大，对吧？
> 🔴 **所以我们是不是可以为了速度稍微做快一点，比如说一次做一个中阶段。**」

#### 🔴 为什么可以改 —— 🔴 但**只对「同风险」的中阶段有效**

🔴 **上一轮（10-22）拆成「一条指令 = 一个施工步」**，🔴 理由是怕一次做太多出错定位不到。
🔴 **但那一轮真正的原因是「我的指令写坏了」** —— 🔴 指令里写了后续步骤编号，AI 顺着做完了整个 P1。

✅ **那两条已经修好了**（顶部禁令 + 禁写后续步骤编号）→ 🔴 **所以可以放宽**。

🔴 **但放宽的边界在这儿** —— 🔴 **一个中阶段内部的几块，风险必须同档**：

| 风险档 | 例子 | 能不能合成一条指令 |
|:--:|:--|:--|
| 🟢 **低** | 纯算术 · 只调自己的模块 · 不碰别阶段 | ✅ **可以合成** |
| 🟡 **中** | 会碰跨日 · 会改状态字段 | ⚠️ **要单独一条** |
| 🔴 **高** | 会改 P1 已验收的代码 · 会碰界面 | ❌ **必须单独一条** |

🔴 **P2 中阶段 2.A 就是低档** —— 🔴 扣补给 + 断粮惩罚 + 跨日那条链，
🔴 **三块都不碰 P1、不碰界面** → 🔴 **合成一条指令是安全的**。

#### 🔴 三条配套规矩（放宽后必须更严）

| # | 规矩 | 为什么 |
|:-:|:--|:--|
| 🔴 **1** | 🔴 **「不许偷偷挂上去」的检查照旧要贴输出** | 🔴 合成之后更需要看它有没有乱挂 |
| 🔴 **2** | 🔴 **基线测试数要写死**（本中阶段做完应该是多少文件多少条） | 🔴 一次做多了，🔴 **更需要核对数** |
| 🔴 **3** | 🔴 **回执必须写「⏹️ 已停」** | 🔴 一次一个中阶段，🔴 **它做完就该停，不是做完整个 P2** |

> 🔴 **不变的两条**：🔴 **一次只发一条指令** · 🔴 **一个中阶段 = 一次验收**。

### 📌 历史：一条指令 = 一步（🔴 2026-10-22 的规矩 · 🔴 10-23 已放宽为「一个中阶段」）

> 🔴 **这一节保留是因为它记着「为什么出过一次事」** —— 🔴 **教训不能丢**。
> 🔴 **现在的规矩看上面那一节。**

> 🔴 **项目主原话**：「一个大阶段不是分成好几个小阶段吗？
> 🔴 **你是怎么做到发送一个指令就直接跨过了一个大阶段的？**」

### 🔴 事实

🔴 **2026-10-21 18:35 我只发了第 2 步的指令** · 🔴 **Hermes 从第 2 步一路做到第 5 步**，🔴 连验收表都生成了。

🔴 **根因 —— 我的指令里写着「第 3 步」「第 4 步」「第 5 步」**，🔴 它读到编号，
🔴 🔴 **自然以为要把整个 P1 做完**。

### 🔴 缺的三样（🔴 全是我的问题）

| # | 缺什么 | 后果 |
|:-:|:--|:--|
| 1 | 🔴 **没写「做完这一步就停」** | AI 默认「把这件事做完」= 做完整个阶段 |
| 2 | 🔴 **「这一步明确不做」只列了功能** | 🔴 **只能防功能膨胀，防不住跨步** |
| 3 | 🔴 **没说「等下一条指令」** | AI 不知道该不该停 |

### 🔴 三条新规矩（🔴 每条指令顶部必须有）

| # | 规矩 |
|:-:|:--|
| 1 | 🔴 **顶部第一段写「做完这一步就停 —— 等下一条指令，不许继续往下做」**（🔴 不许藏在末尾） |
| 2 | 🔴 **「这一步明确不做」分两栏**：不做什么功能 · 🔴 **不许做后面的步骤** |
| 3 | 🔴 **回执里要写「⏹️ 已停」** —— 🔴 **这样我能一眼看出它没继续往下做** |

> 🔴 **补丁全文** → `AI交流\HERMES_补丁_一条指令只做一步.md`
> 🔴 **六条指令已全部补上**（P1 五条 + P2 第一条）。

### 🔴 顺带一条：🔴 **别在指令里写后面的步骤编号**

🔴 **想提「下一步是什么」的时候，🔴 只能写在「🔴 这不在本步范围」那一栏**，🔴
🔴 🔴 **不许写成「第 3 步要做 X」** —— 🔴 **AI 会把那句话当待办**。

## 五之四、🔴 🔴 改代码前的规矩（2026-10-23 项目主定）

> 🔴 **项目主原话**：「🔴 **写新的代码之前要把旧代码备份一次。**」

### 🔴 规矩一：🔴 **改现有代码前，先备份一次**

| 项 | 规则 |
|:--|:--|
| 🔴 **1** | 🔴 **在已有代码上改功能之前**，🔴 **先把当前代码快照一份**到 `90_历史与废案/` |
| 🔴 **2** | 🔴 **快照要带日期和「为什么备份」** | 🔴 例：`19_改代码前快照_20261023_改UI前.md` |
| 🔴 **3** | 🔴 **快照里要写清楚「这次要改什么」** | 🔴 不然三个月后没人知道备份的是哪一版 |

### 🔴 规矩二：🔴 **不新建代码目录**

🔴 **P1→P2→P7 都在 `src/pNN/` 里加文件**，🔴 **不许另开一个 `src/p2-新/` 之类**。
🔴 **理由**：🔴 阶段目录就是给代码分组的，🔴 再开一层等于自己给自己制造「哪份是真的」的问题。

### 🔴 规矩三：🔴 **git 历史本身就是第二道备份**

🔴 **217 条 commit · 任何一版都能 checkout 回来** —— 🔴 所以备份不是为了「找回」，🔴
🔴 **是为了「对比」**：🔴 改完之后能一眼看出「跟备份比变了什么」。

> 🔴 **⚠️ 但 git 有一个盲区** —— 🔴 **未被 git 跟踪的文件不在历史里**。
> 🔴 所以备份要在 **commit 之后、动手之前**做，🔴 **这样快照里的东西一定在历史里**。

## 八、🔴 项目执行原则

| # | 原则 |
|:-:|:--|
| 1 | 🔴 **先建立最小可运行、可测试的基础**，再逐步增加游戏系统 |
| 2 | 🔴 **旧代码停止作为正式实现基础**，但已有设计规则和有效经验可以继续使用 |
| 3 | 🔴 **不为了重写代码而重写已经明确的设计规则** |
| 4 | 🔴 发现权威规则冲突时**先明确问题**，🔴 **不允许 AI 自行猜测** |
| 5 | 🔴 每个中阶段结束后，必须执行**自动验证 → 进度同步 → 项目主人工验收** |
| 6 | 🔴 每个中阶段通过后，建立**可追踪的版本节点**，🔴 确保出现回归问题时能定位和恢复 |
| 7 | 🔴 每个阶段**只实现当前范围需要的内容**，不提前扩大到后续系统 |
| 8 | 🔴 **自动测试通过不代表系统设计正确**，🔴 也不代表游戏体验已经合格 |
| 9 | 🔴 **项目主不必先成为程序员才能推进项目** —— 代码架构说明、操作步骤和测试结果都应当让非程序员能够理解 |
| 10 | 🔴 任何阶段**只有在达到出口条件并同步进度后**，才能标记为"已通过" |

> 🔴 **本规划的最终目的**：🔴 让《余烬商队》的开发过程**可追踪、可验收、可恢复**，🔴 减少项目主在多个 AI 和多份文件之间人工同步状态的负担。
