## 2. 🔴 本次要做出什么

### 2.1 目录与文件

```
游戏本体\src\p1\
├─ README.md            ← 目录说明（我已建好，你要改就改）
├─ 架构说明.md          ← 🔴 你这次的核心产出之一
├─ 状态.ts              ← 游戏状态类型（先只放最少的字段）
├─ 入口.ts              ← 演示入口：跑一次操作，打印结果
└─ 入口.test.ts         ← 入口的测试
```

> 🔴 **只建这五个。** 🔴 **不要提前建地图/时间/体力/天气/路况的模块** —— 🔴 那是 1.1~1.3 的活。
> 🔴 **1.0.0 的目的是「架构立起来 + 能跑起来 + 项目主看得懂」，🔴 不是功能。**

### 2.2 `架构说明.md` 必须写清的五件事

🔴 **这是给小烬之外的"非程序员"看的** —— 🔴 项目主明确要求「不必先成为程序员才能推进项目」。

| # | 要写什么 | 🔴 验收标准 |
|:-:|:--|:--|
| 1 | 🔴 **每个文件负责什么** | 一句话一个文件，🔴 不许用"封装""抽象"这种术语 |
| 2 | 🔴 **游戏状态里有什么、谁改它** | 一张表：字段 · 谁写 · 谁读 |
| 3 | 🔴 **一次操作走哪几个文件** | 一条流程（文字箭头就行） |
| 4 | 🔴 **怎么跑测试、结果在哪看** | 🔴 复制粘贴能跑的命令 |
| 5 | 🔴 **怎么改一行代码看到效果** | 🔴 改哪 → 跑什么 → 期望看到什么 |

> 🔴 **第 5 条最重要** —— 🔴 **它决定项目主能不能自己验证。**

### 2.3 `入口.ts` 要做到什么

🔴 **一个能跑起来的最小演示**：

```
运行入口.ts → 打印：现在第几天、几点、体力多少、在哪
              → 做一次"走一格"（🔴 这一格先写死坐标或用一个最简的假地图）
              → 再打印一次 → 打印两次的差别
```

🔴 **要求**：
- 🔴 **必须能在终端直接看到输出**（`npx vitest run` 里能看见，或者 `npx tsx` 能跑 —— 🔴 你选，但要说清楚怎么跑）
- 🔴 **不许只是"函数定义了但没人调用"** —— 🔴 必须真的跑一次并打印
- 🔴 打印要**全中文**，带具体数字（🔴 项目主要看数字，不看代码）

### 2.4 `入口.test.ts` 要覆盖什么

🔴 **至少 4 条**：

| # | 断言 | 🔴 为什么 |
|:-:|:--|:--|
| 1 | 🔴 入口能跑完不报错 | 基本可用 |
| 2 | 🔴 初始状态的字段是预期的值 | 状态结构对不对 |
| 3 | 🔴 "走一格"之后**该变的变了** | 🔴 状态更新对不对 |
| 4 | 🔴 "走一格"之后**不该变的没变** | 🔴 有没有误改别的字段 |

> 🔴 **第 4 条最容易漏，但最重要** —— 🔴 它抓的是"改 A 把 B 也改了"这类 bug。

### 2.5 🔴 项目主看得懂的架构图（§2.2 第 1 条的一部分）

🔴 **一张图**（ASCII 或 Mermaid 都行，🔴 **只要在 `架构说明.md` 里能直接看到**）：

```
[入口.ts]  →  [状态.ts]
   ↓            ↑
（改状态）  （读状态写状态）
```

🔴 **不许只写代码目录树** —— 🔴 目录树不说明"谁调用谁"。
